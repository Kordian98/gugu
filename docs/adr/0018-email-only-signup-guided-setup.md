# ADR-0018: Email-only signup, lazily created draft salon, server-side guided setup

- Status: proposed (amended 2026-11-04: security review M1–M2, L1–L4; owner answers q102–q104; second review: signup gate parity, eTLD+1 domain key, per-source sub-caps)
- Date: 2026-11-04
- Owner: salon-crm (topic 07); touches 05 (salons module, auth screens) and 12 (analytics)
- Context: the owner expects heavy drop-off from the old flow (sign in → a salon form with name, category, phone, province, ward, street → wizard). His brief (2026-11-04): "an email is enough", then a guided, delightful setup where every step feels like progress. X25: Basic free for the first year, 14-day Pro trial first, no payment method ever. q96: trial = Pro features, small AI cap.

## Decision

1. **One field to start.** `/{locale}/business/join` is the existing magic-link sign-in (link + 6-digit code, same rate limits, CSRF and session security) with signup copy. New and existing emails get identical responses and screens, so there is no "account exists" dead end and no enumeration; an existing owner simply lands in their salon. The old salon form screen is removed. `POST /salons/registrations` is **removed** (security review M2 retired its anonymous variant; the follow-up review found the signed-in variant still created salons + trials without the quick-start refusals, abuse brakes or the AI-allowance gate). Nothing in `apps/app` called it and the E2E seed had moved to quick start, so instead of a second copy of the rules (or a platform-admin-only route, which makes no sense while platform admins own no salon) quick start is the **only** salon-creating route, and every refusal and limit lives in one `SignupGuard` (`apps/api/src/modules/salons/application/signup-guard.ts`) that any future salon-creating path MUST call. The route now answers 404 for everyone. Pending salons created before ADR-0018 are still confirmed or declined through `/me/pending-salons`. Both the E2E seed and the local demo seed (`seed-demo-salon.mjs`) use quick start + the business step + `settings/profile`, like the app.
2. **The salon is created when a signed-in user without any salon enters the workspace**, by an explicit, authenticated `POST /salons/quick-start` that `BusinessGuard` (`QuickStart`) calls (not inside magic-link verify). Reasons: verify is shared by staff joining through invitations and by future Apple/Google sign-in; an explicit call keeps the auth module unchanged and works for every sign-in method. Defaults: **no name** (empty string, never shown — q103, see 4), Asia/Ho_Chi_Minh, vi, schema-default booking settings (60-day window), status `draft`, trial + free Basic year (`SubscriptionsFacade.startTrial`), a `salon_setups` row, owner + org-owner memberships `active`, audit `salon.registered` (`via: quick_start`). One transaction under a per-user advisory lock: a double click, a retry or a reload returns the same salon (`created: false`). Refusals: an unconfirmed owner membership from the old anonymous form → 409 `salon.pending_confirmation`; a platform admin (`platformRole` set) → 403 `salon.quick_start_not_allowed` (the app shows "open the admin panel"); a disposable email domain (`DISPOSABLE_EMAIL_DOMAINS`, `packages/domain/src/onboarding/email-domains.ts`) → 422 `salon.email_not_allowed`; a team invitation for the email (open, or one this user accepted before) → 409 `salon.invitation_pending` unless the client sends `ignoreInvitations: true` (see 9).
   **Abuse brakes against trial / free-year farming (security review M1)**, in `SignupGuard`, consumed only when a salon is actually created: 5 per user per day; 20 per client IP /24 (IPv6 /48) per hour and `QUICK_START_IP_DAILY_LIMIT` (default 40) per day, keyed per user when the IP is unknown (never one shared `"none"` bucket, L4); `QUICK_START_DOMAIN_DAILY_LIMIT` (default 20) per **registrable email domain** per day; and a global `QUICK_START_DAILY_CAP` (default 500) per 24 h. The domain key is the eTLD+1 from the ICANN section of the Public Suffix List (`tldts`, bundled list; refreshed with dependency updates), so `a.evil.com` and `b.evil.com` share `evil.com`, `mail.shop.com.vn` shares `shop.com.vn`, and `com.vn` / `.vn` are suffixes, never one bucket for every Vietnamese domain. Private-section suffixes (dynamic-DNS zones and the like) are deliberately ignored, so all their subdomains share one bucket. **No single source can exhaust the global cap:** every bucket except the global one is capped at `QUICK_START_SOURCE_SHARE_PCT` (default 25 %) of it, including large consumer providers (`MAJOR_EMAIL_PROVIDERS`: gmail.com, yahoo.com.vn, outlook.com, …), which skip the per-domain limit but not the share. A refused attempt gives back every hit it counted, and the global bucket is consumed last, so refusals never use up room for others. Alerting: an error is logged once the global count reaches 80 % ("quick-start global daily cap nearly reached") and on every refusal by the cap ("… reached"). Trade-off: on a day when gmail.com signups alone pass 25 % of the cap, further gmail signups wait until the window rolls; the near-cap alert fires well before, and raising the cap is a config change. **The trial's AI allowance starts with the first real setup step:** while `salon_setups.name_confirmed = false`, `EntitlementService` resolves `ai.monthly_cost_cap_vnd` to 0 (an admin override of that key still wins); saving the name invalidates the entitlement cache and the trial's 20,000 VND cap (q96) applies. Everything else of X25/q96 is unchanged (14-day Pro trial from creation, then the free Basic year).
3. **Wizard progress lives on the server** (`salon_setups`: business type, name confirmed, current step, completed/skipped steps, wizard closed/finished, card dismissed). It is resumable on any device; the Today redirect into the wizard and the Today "finish setup" card read it. What is still *open* (`remaining`) is always computed from real data (name confirmed, opening hours, active services, a bookable staff member, a connected Zalo OA), never from clicks, so work done outside the wizard counts.
4. **The name is required first (owner q103: no default name).** Quick start stores an empty name (salon and organisation), never a placeholder, and `name_confirmed = false`. The workspace's `NameGate` sends every business route to the setup's name step until a valid name (trimmed, 2–80) is saved; that step has no "skip" and no "later". Server side, everything that needs or shows the name refuses with 409 `salon.name_required` until then: setup progress (except viewing the name step), the Today card, template services, Zalo OA connect, team invitations (`assertSalonNamed`, salon-settings facade). The business type on the same screen is optional. The onboarding checklist's `business` step is done when the name was confirmed *or* (older salons) phone + address exist; `remaining` (the Today card) never contains the name.
5. **"Go live" happens by itself** once the wizard is closed and the checklist is complete. With no public salon page (X23), `draft` vs `active` only ended the checklist, so an extra button would be pure friction. Salons from the old form keep the old checklist card and its button.
6. **Minimal server-side analytics now** (X14): table `analytics_events` (name, salon id, salted `actor_hash`, PII-free props, time) and a strict Zod catalogue `ANALYTICS_EVENTS` in `@gugu/contracts`, written by `AnalyticsService` (global module `analytics`). Only the signup funnel uses it so far. Topic 12 still owns the full pipeline (`packages/analytics`, partitioning, rollups, consent-gated client events) and can migrate these rows. The catalogue lives in contracts, not `packages/analytics`, because that package does not exist yet.
7. **Delight inside the calm brand.** The wizard is the one place in the workspace with motion: a progress ring, a check pop and a short confetti burst in Lilac Glow colours on completion, haptics on native (`expo-haptics`, added), all skipped with reduced motion. No 3D, glass or gradients; tokens only; light and dark.
8. **Zalo connect can return to the wizard**: `POST zalo/connection/start` takes `returnTo: "settings" | "setup"` (an enum, never a URL, so no open redirect); the callback then lands on `/business/setup?step=zalo&zalo=<result>`.
9. **Invited staff never get an empty salon (owner q102).** `QuickStart` first asks `GET /me/invitations` (open invitations bound to the user's verified email): with any, it shows "Anh/chị được mời vào <Salon>. Tham gia?" (one card per invitation) and `POST /me/invitations/:id/accept` joins without the link token (email-bound invitations only; the same accept logic as `/invitations/accept`: seats, suspension, single use). Only the explicit "Tôi là chủ salon, tạo salon mới" calls quick start with `ignoreInvitations: true`. A user who accepted an invitation before and now belongs to no salon also chooses explicitly. **Clean-up of the earlier bug:** when a user accepts an invitation (either route), every salon they own that was never named (an untouched quick-start salon — the name is the mandatory first step) is archived: `deleted_at` set (it vanishes from `/me` and every query), their membership `removed`, audit `salon.archived_unused`. Named salons are never touched.
10. **Which salon opens first.** `/me` lists memberships most recently joined first; the workspace opens the salon last picked with the switcher on this device (web: `localStorage`), else the first in that list — so right after accepting an invitation the user lands in the inviter's salon.
11. **Setup rows only from quick start or the business step (L2).** `progress` and `dismiss-card` answer 404 for salons without a `salon_setups` row and never create one; saving the business step creates it for older salons.
12. **Analytics privacy (L3).** Events are pseudonymous with no direct identifiers: ids, enums and counts; the actor as an HMAC keyed with a dedicated `ANALYTICS_HASH_SECRET` (required in production, never `AUTH_SECRET`). The daily retention job deletes events older than `ANALYTICS_RETENTION_MONTHS` (default 24).
13. **Trial notice (owner q104).** Today shows "Pro trial ending soon" only in the last 3 days of the trial (`TRIAL_ENDING_NOTICE_DAYS`); the free-year notice keeps its 14 days.

## Consequences

- A user who signs in through the generic sign-in page and has no salon and no invitation gets one automatically (before: the registration form). Invited staff are offered their invitations instead (q102).
- Unnamed salons exist in the database (empty name) until the owner names them; admin lists may show them without a name, never with a made-up one. Slugs are random (`salon-xxxxxx`; salons have no public page, X23).
- Invitations without an email (link-only) cannot be matched to a signed-in user; those users still join through the link.
- `analytics_events` is a second, smaller analytics store until 12 lands; the event names are the contract to keep.
- The wizard writes through the normal settings/catalog/team endpoints; only the business step, progress, card dismissal and template services are new endpoints.
